# Porting dzkit to another language

How to build a dzkit package for a new language or framework (PHP, Python, Dart, Laravel, Symfony…) that gives exactly the same results as every other one. [dzkit-js](https://github.com/dzkit/dzkit-js) is the reference implementation; read its code when this page isn't enough, and open an issue here when you find something this page should say.

## 1. What a port is

A port has three parts:

| Part | Comes from | Written by hand? |
|---|---|---|
| **Data**: wilayas, phone blocks, IRG scale, CNAS rates… | `dist/dzkit-spec.json` | No: generated by a script |
| **Behaviour**: parsing, keys, rounding, errors | [OPERATIONS.md](OPERATIONS.md) | Yes |
| **Tests**: the shared test cases | `dist/vectors.json` | The runner only; the cases come from here |

A port is finished when it provides **every operation** in OPERATIONS.md and passes **every case** in `vectors.json`. Framework packages (Laravel, Symfony…) don't re-implement anything: they wrap a core package of the same language (§ 9).

## 2. Names

**Repository:** `dzkit/dzkit-<language>`: `dzkit-php`, `dzkit-python`, `dzkit-dart`; framework packages `dzkit-laravel`, `dzkit-symfony`.

**Package:** follow the registry's custom, keeping `dzkit` visible: `@dzkit/dzkit-js` on npm (npm refused the bare name `dzkit`), `dzkit/dzkit-php` on Packagist, `dzkit` on PyPI and pub.dev when available.

**Functions:** one per operation, named in the language's style. Keep the same words so a developer moving between languages recognises them:

| Operation | JavaScript | PHP | Python |
|---|---|---|---|
| `rip.validate` | `isValidRip`, `parseRip` | `isValidRip`, `parseRip` | `is_valid_rip`, `parse_rip` |
| `rip.from-ccp` | `ccpToRip` | `ccpToRip` | `ccp_to_rip` |
| `phone.format` | `formatPhone` | `formatPhone` | `format_phone` |
| `irg.calculate` | `calculateIrg` | `calculateIrg` | `calculate_irg` |
| `salary.gross-to-net` | `grossToNet` | `grossToNet` | `gross_to_net` |
| `words.amount-ar` | `amountToWordsAr` | `amountToWordsAr` | `amount_to_words_ar` |

Fields follow the same rule: the test cases use snake_case (`cnas_employee`, `area_code`); JavaScript returns `cnasEmployee`, Python `cnas_employee`. The test runner maps them.

Grouping functions in classes or namespaces (`Dzkit\Phone::format()` in PHP) is fine, as long as each operation has one obvious entry point.

## 3. Using the spec

1. **Pin a release.** Never follow `main`. Download the files of one release:
   ```
   https://github.com/dzkit/dzkit-spec/releases/download/v0.4.0/dzkit-spec.json
   https://github.com/dzkit/dzkit-spec/releases/download/v0.4.0/vectors.json
   https://github.com/dzkit/dzkit-spec/releases/download/v0.4.0/SHA256SUMS
   ```
   Check them with `sha256sum -c SHA256SUMS`, then commit them in the port (for example in `spec/`), so builds and tests work offline and the pinned version is visible in the repository. dzkit-js pins the release archive in `package.json` instead; either is fine.
2. **Check `schema_version`.** Your generator and test runner must refuse a format version they don't know (currently 3), so a format change fails loudly instead of being half-read.
3. **Generate the data.** Write a small script that reads `dzkit-spec.json` and writes a source file of constants in your language, with a header saying it is generated and from which spec version. Never copy values by hand. Run it again in CI and fail if the output changed (`git diff --exit-code`).
4. **Expose the spec version** as a constant (`SPEC_VERSION` in dzkit-js) and say it in the CHANGELOG of each release.
5. **Pick rule versions by date.** Most rules have one version in force today, but the code must choose the version for the requested date (OPERATIONS.md § 1.4), not just the last one.

## 4. The test runner

Load `vectors.json` and, for each suite, map `operation` to your function. For each case:

| The case has | Your test checks |
|---|---|
| `"expected": { … }` | the result has every field listed, with the same value. A field whose expected value is `null` isn't pinned yet: skip it |
| `"expected": null` | the input is rejected: your "nothing" value (`null`, `None`), or `valid: false` for validators. No exception |
| `"error": "<code>"` | the call fails with your dzkit error carrying that code |

Also make the runner fail when `vectors.json` contains an operation your port doesn't map, so a new operation in the spec can't be skipped silently. Compare numbers as numbers (`3100` equals `3100.0`), text exactly, character for character.

## 5. Errors

Each port has one error type carrying a `code`, one of those in OPERATIONS.md § 1.1:

| Language | Shape |
|---|---|
| JavaScript | `class DzkitError extends Error { code }` |
| PHP | `final class DzkitException extends \RuntimeException` with `public readonly string $errorCode` (PHP's own `getCode()` is an integer, so don't use it for the code) |
| Python | `class DzkitError(ValueError)` with a `code` attribute |
| Dart | `class DzkitException implements Exception` with a `code` field |

Validators, parsers and formatters never throw, whatever they receive (OPERATIONS.md § 1.1). Typed languages still accept "any value" where the contract says so: `mixed` in PHP, `object` / `Any` in Python, `Object?` in Dart.

## 6. Numbers: never round with floating point

Payroll and amounts must be exact. The JavaScript port does all money arithmetic in **whole centimes** (and tenths of a centime inside the IRG), with `BigInt` where products can exceed 2^53. Do the same:

| Language | Use |
|---|---|
| PHP | `int` (64-bit) for centimes; `brick/math` or `bcmath` where products can overflow. Don't use `round()` on floats for money: it pre-rounds and doesn't always match half-up on the decimal value |
| Python | `int` for centimes, `decimal.Decimal(str(amount))` to read an amount, `fractions.Fraction` for the smoothing formulas |
| Dart | `int` on the VM; `BigInt` when compiling to the web, where `int` is a 53-bit double |

To read an amount given as a binary float (`1.005`), round half up on its **shortest decimal representation** (`"1.005"` → 101 centimes), not on `amount × 100` (`100.4999…`). See OPERATIONS.md § 1.3 and dzkit-js `toCents`.

The IRG test cases include every boundary and exact half; if your port passes them all, the arithmetic is right.

## 7. Text

- Convert Arabic-Indic digits (U+0660–0669 and U+06F0–06F9) to 0–9 before parsing, then match **ASCII digits only**: in Python, `str.isdigit()` and `\d` also accept Arabic-Indic and other digits, so use `[0-9]`.
- "Whitespace" means every Unicode space, including U+00A0 and U+202F. In PHP use `preg_*` with the `u` flag and `\s` or `\p{Zs}`; `trim()` doesn't remove U+00A0.
- Arabic output must match the test cases exactly, character for character. Don't let an editor or a formatter add marks or change the hamza forms.

## 8. Dates

Days are Algerian days: UTC+1 all year (Algeria has no daylight saving time). A date option accepts the language's date type and an ISO `YYYY-MM-DD` string. "Today" means today in Algeria, not on the server.

## 9. Framework packages

A framework package (`dzkit-laravel`, `dzkit-symfony`) depends on the core package of its language and adds only what the framework needs:

- **Laravel:** validation rules (`new DzPhone(type: 'mobile')`, `'rip' => ['required', new DzRip]`), Eloquent casts (a `ParsedPhone` value object), translations of the error messages in fr, ar and en.
- **Symfony:** validator constraints (`#[DzRip]`, `#[DzPhone(type: 'mobile')]`), form types, a bundle with configuration.

No rule, number or formula lives in a framework package. When the core changes a result, the framework package releases the same kind of version (see GOVERNANCE.md).

## 10. Repository checklist

Copy dzkit-js where it fits:

- [ ] **README** in English, with `README.fr.md` and `README.ar.md`: what it does, install, one example per area, "Input, errors and dates", then the shared ending: **Sources**, **Not legal advice**, **Contributing**, **License**
- [ ] **LICENSE**: MIT, `© Siroukane and the dzkit contributors. Official texts belong to their publishers.`
- [ ] **CHANGELOG.md**: `## X.Y.Z — YYYY-MM-DD` sections, saying which dzkit-spec version each release follows
- [ ] **CONTRIBUTING.md**: setup, rules of thumb (no value without a source; values change in dzkit-spec, not here), releasing
- [ ] **Versions**: the shared rule in [GOVERNANCE.md](GOVERNANCE.md). A fix that makes a wrong result right is a patch; anything that changes a correct result, removes something, or turns a result into an error is a minor version before 1.0
- [ ] **No runtime dependencies** where the language allows it (except an exact-number library if the language has none built in)
- [ ] **Public API pinned by a test**, so internal helpers can't leak into it
- [ ] **CI**: the generated data is up to date, every shared test case passes, on every supported runtime version
- [ ] **Release workflow**: runs when a GitHub release is published; one job builds and tests without publishing rights, a second job only publishes; actions pinned to commits; no stored tokens:
  - **npm:** trusted publishing (OIDC), with provenance;
  - **PyPI:** trusted publishing (OIDC) with `pypa/gh-action-pypi-publish`, with attestations;
  - **pub.dev:** automated publishing from GitHub Actions (OIDC);
  - **Packagist:** nothing is uploaded: Packagist reads the Git tag through the GitHub hook. Protect release tags (repository rulesets) so only maintainers can create them, since the tag *is* the release.
- [ ] **Issue templates** pointing value changes to dzkit-spec

## 11. When the spec changes

Every dzkit-spec release lists its changes in [CHANGELOG.md](CHANGELOG.md). To follow it: pin the new release, regenerate the data, run the test cases, and fix what fails. If no result changes, release a patch; if results change, a minor version before 1.0 (GOVERNANCE.md).
